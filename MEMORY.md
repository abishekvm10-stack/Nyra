# Nyra — Working Memory

Read this before starting new work on this project; update it after every meaningful change instead of re-deriving history from git log / re-reading the whole tree each session.

## What this is
Electron tray/menu-bar app ("Nyra", package name `nyra-desktop`), at `d:\Nyra\files\promptos-desktop\` (this is the project root — flattened 2026-08-18, was previously double-nested at `...\promptos-desktop\promptos-desktop\`). User copies text anywhere, presses a global hotkey (Alt+P), Nyra reads the clipboard, sends it to an LLM provider — **Nyra Cloud** (free, shared, no key, via the deployed `backend/` proxy — the default), Groq, Local/Ollama, or OpenAI/Anthropic/Gemini, see `compiler.js` — to "compile" it into a structured prompt, writes the result back to the clipboard for the user to paste. As of 2026-08-19, the compiled shape adapts by **task type** (code/writing/analysis/research/creative/general) **and target agent** (see `prompt-kit.js`) instead of one fixed Role/Context/Task/Constraints/Output-Format template — that template is now just the `general` task type's shape. Targets both Windows and Mac from one codebase (`electron-builder`, `npm run build:win` / `build:mac`).

## Gotcha: "the new version isn't installing" is usually the single-instance lock
Hit this on 2026-08-19 and it burned real time, so: `app.requestSingleInstanceLock()` ([main.js](main.js) line ~14) means **any running Nyra — including a dev-mode `npm start` from hours earlier — silently swallows the launch of a newly-installed build.** The new copy fails to get the lock, calls `app.quit()`, and its `second-instance` handler tells the *old* instance to show its window. The user clicks the new Nyra and sees the old one, with the old version number.

Diagnostic that actually settles it, rather than guessing at the updater:
```
Get-CimInstance Win32_Process -Filter "Name='electron.exe' OR Name='Nyra.exe'" |
  Select-Object ProcessId, Name, CreationDate, CommandLine
```
A `CommandLine` ending in `electron.exe .` is a dev instance; a path under `...\Programs\Nyra\` is the installed one. Note the **start time** — a running process reports whatever `package.json` version existed *when it launched*, so editing the version in the file never changes what a live instance displays. Kill it, then launch the installed app.

Two related signals that look like bugs but aren't: "Check for updates" returning *"Update checks only run in the installed app, not in development"* just means `app.isPackaged === false` (i.e. it's the dev instance, working correctly), and **v0.2.4 and earlier could never check for updates at all** — `setupAutoUpdater()` was only wired into the `second-instance` handler, never `app.whenReady()`, until the fix that shipped in v0.3.0. Don't debug the update feed on an old build; check which build is running first.

## Changelog (most recent first)
- 2026-08-19 (same day, app size — found the actual bug): User asked (third time) to get both installers under 50MB. Previous attempts had *deferred* this without diagnosing it; actually measuring it this time found a real, serious packaging bug that had nothing to do with "unwanted files in the codebase."
  - **Root cause: `dist/` was being packed inside `app.asar`.** The `files: ["**/*"]` glob had no `!dist/**` exclusion, so during packaging electron-builder swept the *freshly-extracted 259MB Electron runtime* (sitting in `dist/win-unpacked`) into the app bundle. **The shipped app contained a complete second copy of Electron inside itself.** Measured: `app.asar` was **275MB** while Nyra's entire source tree is **505KB**. This also explains the previously-unexplained mystery from an earlier session where the Mac `.dmg` *grew* from 173MB→187MB during a size-reduction attempt — every rebuild was accumulating more nested build output. Fixed by adding `!dist/**`, `!release/**`, `!backend/**`, `!.github/**`, `!package-lock.json` to all three `files` arrays (top-level, `win`, `mac`). **Result: Windows installer 159MB → 72MB**, `app.asar` 275MB → 17MB. Mac not rebuilt here (no runner) but the same bug and fix apply to `mac.files`.
  - **Also stripped Chromium locales**: Electron ships 55 locale `.pak` files (39MB) to localize its *own* built-in UI (context menus, error pages); Nyra is English-only. New `build/afterPackHook.js` deletes all but `en-US`, plus `electronLanguages: ["en-US"]` and `compression: "maximum"` in `package.json`. Locales 39MB → 464KB. **The hook matches locale files by exact name/extension, never "delete everything except X"** — the macOS Electron Framework `Resources` directory it walks also contains `icudtl.dat` and the `.pak` files Electron cannot boot without, so a blanket delete would have produced a build that packages cleanly then fails to launch. Verified the filter against both the real Windows locales dir (keeps `en-US.pak`, removes 54) and a simulated macOS Resources listing (keeps every runtime file).
  - **≤50MB is not achievable with Electron, and this is now measured rather than asserted**: `Nyra.exe` — pure Chromium/V8/Node containing zero Nyra code — is **172.5MB uncompressed, 75.7MB compressed** on its own. The 72MB installer is already essentially just that binary; everything else in the build compresses into the remaining few MB. The realistic Electron floor is ~65-72MB. Getting to ≤50MB would require **leaving Electron** for a system-webview toolkit (Tauri: 3-10MB apps, uses WebView2/WKWebView instead of bundling Chromium) — which is viable here since the app is only 505KB of logic plus an HTML settings window, but it's a shell rewrite (`main.js`'s tray/hotkey/clipboard/IPC layer → Rust), not a config change. **Not done; flagged to the user as an explicit decision.**
  - **Tried and rejected**: removing `jimp`/`@jimp` (8.4MB of the remaining 17MB asar) — they're image-processing libs Nyra never uses, pulled in by `@nut-tree-fork/nut-js`. Tested empirically by moving them aside: `require("@nut-tree-fork/nut-js")` throws `Cannot find module 'jimp'` (eagerly required via `shared/dist/lib/functions/imageToJimp.function.js`), so removing them breaks automation entirely. Restored and re-verified working. Also *not* removed: `LICENSES.chromium.html` (9.1MB) — Chromium's BSD license requires reproducing those notices, so dropping it is a license violation unless they're surfaced elsewhere (e.g. the About tab); worth ~2-3MB compressed, not worth the legal exposure while still 20MB+ over target regardless.
  - **Verified**: clean `rm -rf dist && npm run build:win` from scratch; `app.asar` extracted and audited (all five runtime `.js` files + `settings/` present, correct `main` entry in its `package.json`, nothing excluded that's actually required — confirmed no runtime file requires `backend/`); native modules correctly unpacked to `app.asar.unpacked` with `libnut-darwin`/`libnut-linux` properly excluded from the Windows build (only `libnut-win32` present, confirming the per-platform exclusions added earlier work); stock `electron.exe` and the locale-stripped `Nyra.exe` both initialize and exit cleanly. **Not verified**: a full interactive GUI launch — this sandbox has no desktop session, so the tray app exits immediately regardless of build health. Real launch + tray + hotkey testing must happen on a real machine before trusting this build.
- 2026-08-19 (same day, macOS automation + a real latency fix): User asked whether "Auto select, copy & paste" works on Mac (it didn't — hard-gated to `win32` in three places) and separately reported the feature feels slow on Windows. Planned via Plan Mode, then implemented in full.
  - **Root cause of the latency, found and measured, not assumed**: `@nut-tree-fork/nut-js`'s `KeyboardClass` defaults `config.autoDelayMs` to 300ms, applied as an `await`'d sleep *before* every single `pressKey`/`releaseKey` call — `automation.js`'s `sendShortcut()` makes 6 such calls per shortcut (two `releaseModifiers()` sweeps plus press/release pairs), so a full copy+paste cycle burns ~5.9s of pure sleep, separate from the actual compile network call. Fixed by setting the delay to 10ms (not 0ms — leaves headroom for slower targets) on both the JS-side `keyboard.config.autoDelayMs` **and** the native-side cache (`providerRegistry.getKeyboard().setKeyboardDelay()` — assumed, wrongly, that setting only one would suffice until checked). **Measured directly against the real module** (not a mock): 300ms profile averaged 6.2s for select-all+copy+paste, the new 10ms profile averaged 0.87s — roughly a 7x speedup. A `setSpeedProfile("safe")` fallback (back to 300ms) is retried once automatically in `main.js`'s `handleHotkey()` if a fast-profile capture comes back empty, so a target app too slow for 10ms degrades to today's old behavior instead of just failing.
  - **macOS keystrokes added**: `automation.js` now sends ⌘ instead of Ctrl on `darwin` (`PRIMARY_MODIFIER`). Caught a real bug while doing this in the sandbox (this machine is Windows, so it could be tested directly): `Key.LeftCmd`/`RightCmd` throw `"Invalid key code specified"` on the win32 native backend — they are not a cross-platform-safe modifier the way `Key.LeftSuper`/`RightSuper` are (verified both directly against the installed `libnut-win32` binding). The initial edit unconditionally added Cmd to `releaseModifiers()`'s sweep, which would have broken Windows automation; fixed by building the modifier list conditionally on `IS_MAC` and lazily (not at module scope, since `Key` is `undefined` whenever the native module fails to load — a module-scope array referencing `Key.X` would have thrown on import in that case).
  - **macOS permission model**: uses Electron's own `systemPreferences.isTrustedAccessibilityClient()` rather than trusting `libnut-darwin`'s bundled `permissionCheck.js` — that file depends on the *optional* `@nut-tree-fork/node-mac-permissions` package (not installed in this project's lockfile) and silently no-ops the permission check if it's missing, meaning keystrokes would just do nothing with no prompt ever shown. New `main.js` helpers: `automationPlatformSupported()`, `accessibilityStatus(prompt)`, `automationBlockedReason()` — replacing the three scattered `=== "win32"` checks (in `automationUsable()`, the tray menu's `enabled:`, and `runAutomationSelfTest()`'s early return) with one source of truth. **Important caveat for future-self**: `AXIsProcessTrusted` caches per process, so a grant made while Nyra is running won't be reflected until relaunch — Settings now has a "Relaunch Nyra" button for exactly this. Also: TCC grants are keyed to the code signature, and Nyra is only ad-hoc signed (`codesign --sign -`), so **every rebuild/update requires the user to re-grant Accessibility access** — this is a real, recurring UX cost, not a one-time setup step, until Nyra has a paid Developer ID cert.
  - **Packaging risk identified and fixed proactively, not yet build-tested**: `build/afterSignHook.js` previously did one `codesign --sign - --force --deep` on the whole `.app`. `--deep` does not reliably descend into `Contents/Resources/app.asar.unpacked`, which is exactly where `libnut-darwin`'s native `libnut.node` lands (per `asarUnpack` in `package.json`) — an unsigned Mach-O fails to `dlopen` on Apple Silicon, which would have silently broken automation (or possibly the whole app launch) despite this session's other fixes. Rewrote the hook to glob every `.node` under `app.asar.unpacked` and sign each individually *before* signing the bundle, then run `codesign --verify --deep --strict` and let it throw (failing the build) on any gap. **Not yet verified on a real Mac build** — this sandbox has no macOS runner.
  - **package.json**: `mac.files`'s blanket `!node_modules/@nut-tree-fork/**` exclusion (from the earlier size-reduction pass) is gone — it was excluding the very code this feature needs. Replaced with narrower excludes of the *other* platforms' native binaries (`libnut-win32`, `libnut-linux`) on both `mac.files` and a new symmetrical `win.files`. Checked the actual size impact before assuming it mattered: the whole `@nut-tree-fork` tree is ~2.4MB, so this is roughly a 1MB swing either way — nowhere near where the still-unexplained 187MB Mac `.dmg` bloat actually lives (that investigation is still deferred, unrelated to this change).
  - **Settings UI**: automation card's sub-label and unavailable-hint text became platform-derived instead of hardcoded "Windows"; new `#accessibilityRow` (status + "Grant access…" button, calls a new `nyra:request-accessibility` IPC that prompts via `isTrustedAccessibilityClient(true)` and falls back to deep-linking `x-apple.systempreferences:...Privacy_Accessibility` on refusal) and `#relaunchRow` (calls new `nyra:relaunch` IPC — `app.relaunch(); app.quit()`), both macOS-only and hidden otherwise. New `nyra:automation-status` IPC backs a live check on Settings load rather than trusting a cached field, since a grant made outside Nyra (System Settings) wouldn't be reflected in stored settings.
  - **Verified**: `node -c` on every edited file; `package.json` JSON-parses; the real `automation.js` module loaded and exercised directly in this (Windows) sandbox — `releaseModifiers()`, `setSpeedProfile()`, and the full `selectAllAndCopy()`+`paste()` cycle all ran successfully post-fix, producing the 6.2s→0.87s measurement above. **Not verified**: anything macOS-specific (Accessibility prompt flow, the afterSign hook's binary-signing behavior, real ⌘-key delivery) — none of it can be exercised without a real Mac and a signed build, which this sandbox doesn't have. - 2026-08-19 (same day, release pipeline fixed properly): Replaced the CI-artifact *workaround* for the broken GitHub Release publishing with an actual fix, and closed the Mac auto-update gap.
  - **Root cause of the duplicate/missing-asset releases**: both per-OS jobs called `electron-builder --publish always`, so two separate processes each independently did a find-or-create against the Releases API for the same tag — producing two release objects per tag with assets scattered across them (v0.2.2 and v0.2.3 both show it). **Fix**: both jobs now build with `--publish never` and upload workflow artifacts; a third `release` job downloads all of them and creates exactly one release via the preinstalled `gh` CLI. Without this being true the whole build-then-release-separately design would have silently killed auto-update.
  - **Caught a real latent bug that would have broken Windows auto-update**, and which only appeared *because* of this change: the built installer was named `Nyra Setup 0.2.4.exe` (with spaces) while `latest.yml` referenced `Nyra-Setup-0.2.4.exe` (with dashes). electron-builder's own publisher was silently sanitizing the filename during upload, hiding the mismatch; `gh release upload` does not, and GitHub converts spaces to dots in asset names — so the uploaded asset would have been `Nyra.Setup.0.2.4.exe` and `electron-updater` would have 404'd looking for the dashed name. **Fix**: explicit `nsis.artifactName: "${productName}-Setup-${version}.${ext}"` so the on-disk name, the manifest URL, and the uploaded asset name are all identical. - 2026-08-19: Rebuilt the prompt-compiling core (`prompt-kit.js`, new). User was dissatisfied with compiled-output quality and specifically suspected per-agent tuning wasn't doing much — correct, and the reasons were structural, not cosmetic. Went through Plan Mode given the size of the change; the approved plan (with a hardening pass added after review) covered a diagnosis, an architecture decision, and 5 named risks each with a fix — see the plan-file history if needed again. Implemented all phases in one pass rather than splitting further, since the pieces are interdependent (adaptive shapes and the sanitizer rewrite had to land together).
  - **Diagnosis**: the old `compiler.js` told the model to "make the most reasonable assumption" for missing details (directly causing invented tone/audience/constraints the user never asked for), and per-agent tuning was one trailing sentence (~40 tokens) fighting a ~300-token instruction that mandated a fixed five-field template — structurally powerless regardless of how good the hint text was. No notion of task type existed at all (a debugging request and an email draft got the identical skeleton), and coding agents (opencode, Cursor, etc.) weren't a category — only chat models were. Also found real bugs in passing: Anthropic alone was capped at `max_tokens: 500` (silent truncation), no provider set `temperature` (nondeterministic compiles), and `backend/server.js` had a dead `projectContext` branch the client never actually populated.
  - **Architecture**: task type (picks *which sections* — code/writing/analysis/research/creative/general) composes with agent profile (picks *how they're rendered* — XML tags for Claude, Markdown headers for GPT/coding agents, flat labels for Gemini/open-weight/generic) inside `prompt-kit.js`, avoiding a hand-written 6×6 template matrix. The compiling model classifies task type itself inside the same call — no second request, no added latency. `getTargetModelLabel()` in `compiler.js` (agent+model string combining, already had a bug fix baked in) was reused unchanged; the family-regex matching philosophy from the old `KNOWN_MODEL_FAMILY_HINTS` was extended into `AGENT_PROFILES`, not replaced.
  - **Coding agents are first-class**: `settings.html`'s `#targetAgent` select gained a "Coding agents" `<optgroup>` (opencode, Claude Code, Cursor, Aider, GitHub Copilot, Codex). Matching order matters and is deliberate — coding-agent patterns are checked *before* the Claude/GPT chat-family regexes in `prompt-kit.js`'s `AGENT_PROFILES`, because "Claude Code" contains the substring "claude" and would otherwise wrongly resolve to the Claude chat profile. This exact ordering bug is now a permanent regression check in `tools/eval-prompts.js`'s structural tier.
  - **Sanitizer rewritten around explicit delimiters** (`===NYRA_OUTPUT_START/END===`) instead of the old literal "Role:" search, which had no fixed anchor to rely on once output shape became adaptive. Writing the sanitizer test suite (`tools/sanitizer.test.js`, 21 cases) caught **two real bugs before they shipped**: (1) the extraction logic used `lastIndexOf` for *both* the opening and closing marker, which broke if a model happened to echo the start-marker text mid-content; fixed by pairing the *last* END with the *closest* START before it — this also turned out to be exactly the right behavior for a model self-correcting mid-response ("actually, let me redo that") with two complete marker pairs, so the fix serves both cases. (2) a request with only a stray END marker and no START fell all the way through to the raw-text fallback, leaving the marker text in the output instead of stripping it. A third bug was caught by mismatched *expectations* in the test file itself, not the code: the conversational-preamble regex (`[^\n]*[:\n]`) was greedy enough to delete an entire first line — including real content like "Role: ..." — whenever a preamble word and a colon both appeared on that line, e.g. "Certainly! Role: ..." crammed onto one line by a model ignoring the delimiter instruction. Fixed by bounding the match and requiring the colon to be followed by a newline, not just present anywhere later in the line.
  - **Prompt-injection defense, added during the hardening pass**: raw clipboard content is arbitrary and untrusted (a webpage's text could contain "ignore previous instructions..."). `wrapUserInput()` wraps the user's actual text in its own `===NYRA_INPUT_START/END===` markers, and the system prompt states plainly that content between them is data to compile, never instructions to follow. Deliberately preserves the user's text byte-for-byte rather than trying to sanitize/strip it — mutating what the user typed was rejected as the same class of failure as the assumption-inventing instruction this whole change removes.
  - **Backend became a thin relay, not a code-sharing exercise**: `backend/README.md` confirms Render deploys `backend/` as its own root directory, so a shared root-level module (the original plan) would have 404'd at runtime — a real, confirmed-not-hypothetical risk caught during a review pass before implementation. Instead `compiler.js` now builds the full system prompt client-side and sends it as a new `systemPrompt` field; `backend/server.js` forwards it to Groq as-is. Its old prompt-building code is kept as a **frozen legacy fallback** (used only when `systemPrompt` is absent, i.e. app versions older than this change) — verified both paths against a locally-run instance of the real Express app (mocking only the outbound Groq call): new-client requests relay the custom prompt verbatim, legacy requests still get the old five-field prompt, and an oversized `systemPrompt` (>4000 chars, a cheap guard added alongside this) is rejected with 400. **This backend change auto-deploys to the live Nyra Cloud backend via Render on push to `main`** (confirmed earlier this project has auto-deploy enabled) — it's the default provider, so this is the one part of this change with real production blast radius; backward compatibility was verified locally before pushing, not assumed.
  - **Settings UI**: new "Task type" dropdown next to AI agent/Model in the Tuning tab, defaulting to "Auto" — an escape hatch for when auto-classification keeps guessing wrong for a particular workflow, rather than chasing perfect classification. `main.js`'s `getSettings()`/`store` gained a `taskType` field; `addHistoryEntry()` now stamps `promptVersion: 2` on new entries so old (pre-this-change) History entries are distinguishable without a migration.
  - **New dev-only tooling** (excluded from the packaged app via `package.json`'s `files`/`mac.files`, `!tools/**`): `tools/sanitizer.test.js` (21-case regression suite, `node tools/sanitizer.test.js`) and `tools/eval-prompts.js` — a structural tier that runs with no network/API key (`node tools/eval-prompts.js`, asserts every agent profile produces a genuinely different system prompt for the same input — the automated version of the user's original complaint — plus the coding-agent ordering regression check) and an optional live tier (`GROQ_API_KEY=... node tools/eval-prompts.js --live`) that compiles 12 fixtures × 6 agent profiles through the real Groq API and checks for hallucinated constraints (via planted "banned terms" per fixture), lost intent, sanitizer leakage, and output bloat, dumping full results to a timestamped file under `tools/eval-output/` (gitignored) for human side-by-side reading.
  - **Verified**: `node -c` on every new/edited file; the sanitizer suite (21/21 passing after the two fixes above); the eval harness's structural tier (all profiles distinct, no ordering regressions); a mocked-fetch integration test confirming `compilePrompt` actually sends the right per-agent system prompt, correct `temperature`/`max_tokens`, and a properly-wrapped user message, with the original raw text preserved byte-for-byte even when it contains HTML/script-like content; a real (non-mocked) local run of `backend/server.js` covering both the new and legacy request shapes plus the oversized-prompt rejection; full `npm install && npm run build:win`, followed by inspecting the built `app.asar` directly to confirm `prompt-kit.js` is actually packaged and `tools/` is actually excluded (not just assumed from the config). **Not yet verified**: real model output quality — that needs a live run with a real `GROQ_API_KEY`, which this sandbox doesn't have; the structural tier proves the mechanism isn't a no-op, but only a live run proves the output is actually *better*.
